# Migrations run at deploy, and the ones written before that never replay

`bun run build` applies the pending migrations before it runs `next build`. The sixteen
migrations that existed on 2026-10-13 are a baseline: on a database that already holds the
site they are never executed, whatever `payload_migrations` says. Only migrations written
after them run on the live database, and those may only add.

This reverses a rule the README used to state on purpose, that migrations are run neither
by `build` nor by `start` and that the operator calls `bun run migrate` at the point they
choose. Andy decided the change on 2026-10-13, on one condition: no path at deploy may
delete, rewrite or move anything Anna has written.

Recorded because both halves will look wrong to the next reader. A build that writes to a
database looks like a mistake, and a list of migration names hard-coded in a script looks
like something to tidy into a timestamp comparison. Neither is.

## Why the build migrates

Coolify deploys when `main` changes and has no step before or after the build. Payload 3.90
reads columns 3.88 did not have (`_objectkey` on `media` and `audio`,
`reset_password_requested_at` on `users`), and a build against a database without them
fails with Postgres error 42703 while collecting page data. That was reproduced here before
anything was changed. So the schema has to be ahead of the build, on every deploy, without
anyone remembering to do it. The build is the only place that is always run.

It also fails in the right direction. If the migration step exits non-zero, `next build`
never starts, no image is produced, and the container already serving the site keeps
serving it.

## Why the old migrations are fenced off

The sixteen were generated by Payload and never meant to be run twice. Their `up` halves
create a type and thirty tables without `IF NOT EXISTS` and add columns the same way; four
of them drop a column; their `down` halves drop every table with `CASCADE`.

Payload decides what to run by reading `payload_migrations`, and what that table holds on
the live database cannot be inspected from here. It may list all sixteen, some, none, only
the `dev` row a development push leaves, or not exist. Left to Payload, a missing row means
"run it". Each was replayed against a copy of today's schema to see: fourteen fail on
their first statement, which would block every later deploy, and two succeed, `spectrum`
and `cta_badge`, re-adding a column that the two migrations written to drop it then drop
again. Nothing is lost on today's schema, by luck of what each statement collides with.
"It happens to fail" is not the condition Andy set.

So the decision is not taken from `payload_migrations`. `src/scripts/migration-plan.ts`
looks at what the database holds:

- **Nothing at all**, not one table in any schema, not even `payload_migrations`: a new
  environment or a CI container. Every migration runs, in order. There is nothing to lose.
- **All thirty tables of the site**: the live database. No baseline migration runs. The
  ones missing from `payload_migrations` are recorded as applied, with a log line each.
- **Anything else**: some tables but not all, tables that are not this site's, the site's
  tables in a schema the connection does not reach, a table of the site that a second
  schema holds too, a `payload_migrations` on its own. The step refuses, changes nothing,
  and the build stops.

A baseline migration is therefore executed only on a database with nothing in it. That is
the whole guarantee, and it does not depend on any bookkeeping being right.

## The rules that follow

- **The baseline is a list of names, and it is closed.** `BASELINE` and `BASELINE_TABLES`
  are written out. A timestamp cutoff would silently move with a renamed file or a clock.
  Nothing is ever added to either list.
- **A migration written after the baseline may only add, and must be safe to run twice.**
  `ADD COLUMN IF NOT EXISTS`, nullable, no default; `CREATE TABLE IF NOT EXISTS`;
  `CREATE INDEX IF NOT EXISTS`. `bun run migrate:create` does not write them that way, so
  the generated file is edited before it is committed. `src/tests/migration-plan.test.ts`
  reads every statement of every ``db.execute(sql`...`)`` in `up` and fails on a `DROP`,
  `DELETE`, `UPDATE`, `RENAME`, `NOT NULL` or a statement without `IF NOT EXISTS`. It
  also fails on anything it cannot read: SQL assembled with `${}`, or a call on `db`,
  `payload` or `req` that is not ``db.execute(sql`...`)``. Nothing checks this at deploy,
  the test is the only barrier. Additive is also what lets the previous build keep
  serving from the database while the new one is being built against it.
- **Removing or rewriting something is not a migration to add, it is a decision.** A column
  that has to go is dropped by hand, after a backup, once no deployed build reads it. The
  test is there to make that a conversation rather than a merged file.
- **One transaction, one lock.** The whole step runs in a single transaction behind an
  advisory lock with a three second `lock_timeout`: two deployments take turns, a failure
  leaves no trace, and the site never queues behind a migration.
- **The step checks its own result.** Before it commits it compares the columns the Payload
  config reads with the columns the database has, and refuses if one is missing.
- **The step refuses to connect with `PAYLOAD_DROP_DATABASE` set, or without
  `DATABASE_URL`.** Payload drops every table as it connects when that variable is `true`,
  whatever `NODE_ENV` is, and the step would then find an empty database, rebuild it and
  report success. So the variable is refused, with any value, before anything connects,
  and since the build is `migrate && next build`, `next build` never connects with it
  either. An empty `DATABASE_URL` is refused for a smaller reason: the driver would fall
  back on the `PG*` variables and migrate whatever database they name.
- **`bun run migrate` is the same script.** There is one way to migrate. `payload migrate`
  is no longer wired to anything, because it is the command that replays.
- **`bun run build` writes to whatever `DATABASE_URL` points at.** In this repository's
  `.env` that is the live database. A local build of a branch carrying a new migration
  applies it to production before the branch is merged. That is safe only because of the
  rule two above, and it is worth knowing.

## What this does not cover

`payload migrate:down`, `migrate:refresh`, `migrate:reset` and `migrate:fresh` are still
reachable through `bun run payload`, and nothing here guards them. Their `down` halves are
the destructive ones. They are not to be run against the live database.

The step is launched with `tsx`, which this project does not list as a dependency of its
own: it is installed because `payload` depends on it, at a pinned version. If a Payload
release ever stops shipping it the build fails at once with `tsx: not found`, in CI first,
and the fix is to add it to `dependencies`.
